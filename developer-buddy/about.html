## Traps (standing)

- Never include the literal phrase “Part of the Buddy System” or the `BUDDY-BASIC-TEMPLATE` marker in a custom page — `gen_basic_homepages.py` treats either as template-managed and will regenerate/wipe it (see buddy-tree `AGENTS.md`).
- Every buddy page ships dark + light mode (`prefers-color-scheme`) — buddy-tree `AGENTS.md` standing rule.
- Extract inline scripts and `node --check` them before any push; verify on the served copy, never announce from a local build.

## Traps learned 2026-10-28
- verify-build.sh RE-RUNS build.py without TZ — the shipped stamp came out UTC (20261028.1540) while the changelog draft said 0840 (PT). Run generators/verify with TZ='America/Los_Angeles' when the stamp matters, and always read the stamp from the served version.txt.
- Snippet extraction: docs/tipjar-snippet.html's own usage prose mentions `<style>` and `<a>` — generators must strip HTML comments before extracting parts, or the prose poisons generated pages (caught mid-run, fixed in both generators).
- gen_default_homepages.py takes explicit buddy ids (`--about` for About pages); running it on v2-era index pages jumps them a template generation — for jar-only changes, swap surgically instead.
- The buddy panel (info panel) must never grow its own search field — Dave's rule (2026-10-28): one filter for the whole dashboard, the main-view Find.
- Panel style (sidebarStyle) persists per origin/device; the default is 'floating'. Dave's Anchored choice on one surface does not carry to others — known confusion source, not a code flip.

## The idea in one paragraph

A new Buddy OS user starts from a **GitHub template repository**: they click "Use this template" and get a clean copy with fresh history — theirs from day one, not a clone of ours. The starter ships the **system only**: the machinery, conventions, and a guided first run. Our buddy-system repo mixes that system with Dave's instance (208 buddies, personal data, flows bound to his repos); the starter is what remains when every trace of the instance is scrubbed out. Its centerpiece is not the files — it's a **first-run setup guide written for the user's own Muse**: their Muse interviews them, creates their first buddy, wires the registry, and builds the first homepage. *Less app, more buddy.*

## Proposed shape

```
buddy-os-starter/
  README.md                  — what this is, the 10-minute tour
  SETUP.md                   — the first-run guide, written for the user's Muse
  AGENTS.md                  — operating conventions (generic form)
  VERSION                    — starter release, e.g. 0.1.0
  CHANGELOG.md               — the starter's own changelog (starts empty of history)
  UPGRADING.md               — "what changed / how to adopt it", per release
  buddies.json               — seed registry: the sample buddies only
  build.py                   — dashboard build (generic form)
  gen_basic_homepages.py     — homepage generator (generic form)
  gen_default_homepages.py   — Dossier + About generator (generic form)
  docs/
    concepts.md              — what a buddy is; system vs instance; the staff metaphor
    registry-format.md       — the buddies.json schema, field by field
    homepage-audition.md     — the homepage rubric (generic form)
    standing-orders.md       — starter standing orders (dark mode, action options, links)
    tipjar-snippet.html      — canonical tip jar, destination blank
    dumpbox-snippet.html     — brain-dump box snippet (generic form)
```

## IN — what the starter ships

### A. First-run bootstrap (the centerpiece)

1. **SETUP.md — a guide written for the user's Muse, not the user.** Step-by-step, in order: (1) interview the user (name, what to call them, timezone, what they care about, who matters to them); (2) explain the system-vs-instance split and that everything created is *theirs*; (3) create their first buddy together (name, parent, persona defaults, icon); (4) wire the registry entry; (5) generate and open the first homepage; (6) walk the dashboard; (7) set up the token-gated write path against **the user's own** GitHub account, with the safety framing (which account, which single permission, what they will see, never paste a token in chat); (8) a "day two" list — briefings, a second buddy, making the repo private/public as they chose.
2. **Interview script outline** inside SETUP.md — the questions, in the order our onboarding learned to ask them, with "skip freely" defaults so setup never blocks on taste decisions (persona/voice/icon get sensible defaults, changeable later).
3. **First-buddy walkthrough** — the worked example: one buddy created start to finish in the guide, matching Sample Buddy #1 below, so the user's Muse can pattern-match instead of improvising.

### B. Core machinery, in generic form

4. **Dashboard (`build.py`)** — the full dashboard build with every owner-specific string parameterized: GitHub owner, repo name, Pages URL, and names read from a single `instance.json` config the setup guide creates. No `davedellaquila` strings anywhere (see the scrub gate in Notes).
5. **Homepage generators (`gen_basic_homepages.py`, `gen_default_homepages.py`)** — same parameterization; the baked-in fleet standards ship as defaults: Files section, baked markdown reader with the `private_files` flag, the full task action set (Done / Need more info / Later / Drop it / ✎ Add a note… + Undo, registry stamps), dark mode, sticky header.
6. **Registry (`buddies.json`) + schema** — the seed registry contains only the sample buddies. `docs/registry-format.md` documents every field (id, name, icon, repo, status, attention + its stamps, links, files, parentage, privacy, voice/persona) so a user's Muse can extend it safely.
7. **Token-gated write helpers** — the client-side write pattern (dashboard + homepage ingest writes, disposition stamps) in generic form, pointed at the user's own repos by the instance config. The *mechanism* is system; every binding to a specific account is instance and is created during setup, never shipped pre-bound.
8. **`.gitignore` + repo hygiene defaults** — no tokens, no local stores, no scratch.

### C. Sample buddies — generic, scrubbed, deliberately few

The v1 set (Dave's call, 2026-11-21): **seven starter buddies defined as brief cards** — the coordinator below is the one fully-worked example the setup guide builds with the user; the other six ship as brief cards the user's Muse fleshes out during setup. The three worked shapes:

9. **Sample 1: a coordinator** ("Project Buddy"-shaped, renamed and re-personed generically) — shows parentage, a dashboard presence, an attention item carrying the full action set, and a homepage that passes the rubric. This is the buddy the setup guide creates *with* the user, pre-built here as the reference.
10. **Sample 2: a simple personal buddy** (a reading/hobby buddy) — shows the lightest viable buddy: registry entry, basic homepage, one ingest-fed section. Proves a buddy can be small.
11. **Sample 3 (optional in v1): a custom-page buddy** — one hand-built homepage beside the generated ones, showing where custom pages plug in and what they must still honor (dark mode, action options, no generator-trap phrases).

Each sample ships as brief cards + finished example pages: the card says what the buddy is for; the pages show the standard met. All names, people, places, and data in the samples are invented for the starter.

### D. Conventions and docs a new user needs in the first hour

12. **AGENTS.md (generic form)** — the operating conventions that make the system behave: git discipline in a shared checkout, verify on the served copy, every named thing gets its link, one topic per message, the critical-items idea (adapted generically), no credential in chat. Written as *a* working model to adopt and edit, clearly marked as a starting point, not a creed.
13. **Homepage rubric (`docs/homepage-audition.md`, generic form)** — the standard a homepage is judged against, including the fleet action standard and dark mode.
14. **Standing orders (`docs/standing-orders.md`)** — the short list: dark mode on every page; action options on every task; newspaper pages get the lightbox; GPX-style domain rules *excluded* (those are Dave's instance, not system).
15. **Snippets** — tip jar (destination blank, filled in during setup), brain-dump box, welcome card.
16. **README.md** — the 10-minute tour: what Buddy OS is, the staff metaphor, what to click first, where SETUP.md takes over.
17. **`docs/concepts.md`** — system vs instance, registry as source of truth, homepages as the buddy's face, "less app, more buddy."

### E. Release machinery (update honesty)

Template copies receive **no** automatic upstream updates — the contents list plans for that instead of pretending otherwise:

18. **VERSION file + tagged releases** — the starter is versioned (semver); each release is a GitHub release with notes.
19. **UPGRADING.md** — per release: what changed, whether it's machinery (safe to copy over), conventions (read and adopt), or schema (migration steps), and a "keep your data" checklist — the Muse-mediated *"update my system, keep my data"* path: the user's own Muse reads UPGRADING.md and applies it to their copy.
20. **Minimal-and-stable bias** — the starter changes slowly on purpose; our working model's experiments land here only once they've proven out (see Notes).

## OUT — deliberately excluded (the scrub list)

Everything personal to Dave's instance. Named by category so the scrub can be checked, not trusted:

1. **The registry's contents** — all 208 of Dave's buddies: ids, names, statuses, attention items, links, files lists, voice/persona picks. The starter's registry holds only the samples.
2. **Personal pages and data** — every buddy homepage/About page from Dave's fleet and everything in them: family members and their details, neighbors' names/addresses/coordinates (the Neighborhood page above all), health and sleep material, money and expense content, vehicles and their records, the Morgan Hill / Llagas Creek sales, Emil's estate, the Lenwood lease.
3. **Private buddy content** — briefs, job reqs, CONFIG/KNOWLEDGE files, ingest logs, decision records, and memory files from Dave's buddies, including Developer Buddy's own paperwork.
4. **Dave-bound flows and identifiers** — his GitHub owner/repo names anywhere in code or docs, his Pages domain and custom domains (fiddletowngazette.com et al.), his Ko-fi destination, his email addresses and phone numbers, his Muse account artifacts (the project-buddy mirror), the buddy-server, API tokens or token-shaped strings of any kind (none ship; the *pattern* ships unbound).
5. **Media** — photos, role-intro and audition audio, avatars, generated artwork from Dave's instance. Samples use placeholder art created for the starter or none.
6. **History** — Dave's CHANGELOG.md and FEATURES.md (the starter starts its own), his git history (template mechanics already guarantee this), his tracked goals, crons, hooks, and briefings machinery tied to his accounts (Gmail/Calendar connectors, Muse Mail address, iPhone routes).
7. **Other products in the fleet** — the Fiddletown Gazette and newspaper system, Money Buddy and the expense tracker, the events database and its API: separate systems that happen to share the fleet, not part of Buddy OS's starter core.
8. **Workspace/VM specifics** — paths, device ids, Tailscale names, local tooling notes (TOOLS.md), and any file whose content only makes sense on Dave's machines.

## Notes for the build phase (not decisions, just recorded)

- **Scrub gate:** before the starter repo is created — and before every release — an automated pass greps the tree for a maintained denylist (owner/repo strings, surnames, domains, addresses, token patterns) and fails the release on any hit. The OUT list above becomes that denylist's first draft.
- **Parameterization is the real work:** the machinery currently hardcodes the instance in a handful of places (owner strings, Pages URL, HERE paths). The build phase extracts those into the instance config the setup guide creates; that extraction, not the file copying, is the schedule driver.
- **Our repo stays the working model.** The starter is a downstream, periodically re-cut export — never a second place where system work happens, or the two drift.
