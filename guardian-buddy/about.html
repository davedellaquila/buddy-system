Guardian Buddy

Executive summary

Guardian Buddy is Dave's security and monetization watchdog for Money Buddy and the buddy system as a whole. It was born from Dave's blunt question: 'it's just raw HTML — what's going to prevent somebody from downloading this, taking my idea, and not sending me money?' Guardian's job is to answer that honestly, build the real protections (legal, technical, strategic), and figure out how Dave actually makes money from these ideas — working in partnership with Buddy Suite, which owns the monetization plan, and the Money Buddy thread.

The idea

A dedicated buddy that thinks about two things Dave can't afford to get wrong: (1) security — how to protect the buddy system and Money Buddy from being ripped off, and (2) monetization — how to turn them into real revenue. Not a product to ship, but a standing advisor and strategist: it holds the threat model, the protection playbook, and the revenue thinking, and it pushes back when Dave's instincts need pressure-testing.

The problem

Dave's fear is legitimate and specific. The Buddies dashboard is a static HTML page on GitHub Pages — anyone can View Source, download it, and re-host it. Money Buddy's client is similarly inspectable. If the idea's value lived in the markup, there would be no defense: you cannot DRM HTML, and obfuscation only slows down casual copiers, never determined ones. Any monetization plan built on 'nobody can see how it works' is a plan built on sand.

How it works

Guardian starts from the honest premise: the HTML is not the product. The protections that actually work: - The moat is the service, not the markup. Money Buddy's value is the Firebase backend, the bank sync, the user's live financial data, the craftsmanship of the experience — the HTML shell without the service is an empty husk. Keep proprietary logic server-side; the client is a window, not the vault. - Legal footing. Copyright notices, terms of service, and trademarked Buddy names. Registration where it counts. Paperwork doesn't stop theft, but it turns theft into something actionable. - The dashboard is a personal tool. Its value is Dave's data and his configured buddies — not transferable by copying the page. If Buddy Suite ever becomes a product, the product is the hosted service with accounts and sync, not the static page. - Speed and brand as defense. Ship fast, build the brand, own the story ('craftsmanship as the differentiator'). Copycats can clone markup; they can't clone momentum. - Partnership, not duplication. Guardian doesn't replace Buddy Suite's monetization plan or the Money Buddy — Monetization & Marketing Plan doc — it pressure-tests them, fills the security gaps, and keeps both honest.

Revenue potential

Guardian doesn't set the revenue targets — Buddy Suite's monetization plan does. Guardian's contribution: making sure the revenue model is actually defensible. Freemium SaaS for Money Buddy (free shell, paid sync/features), the Buddy Suite family as a subscription product line, craftsmanship as the premium justification. Every revenue idea gets the same question: 'what stops someone from undercutting this for free?' — and only the ones with a real answer survive.

Room for growth

  • A formal threat model for Money Buddy (what's client-side, what's server-side, what happens if the client is cloned)
  • Trademark and copyright filing checklist
  • License strategy for the public repos (what's open, what's proprietary)
  • Pricing experiments for Money Buddy once the product is ready
  • Security review of the Firebase rules and API surface before any public launch

Out of scope for v1

Guardian advises and strategizes; it doesn't implement the backend split or file legal paperwork itself — it writes the playbook and hands Dave (or the relevant buddy) the concrete next actions. No FUD, no security theater: every recommendation has to survive 'so what would you actually do on Monday morning?'

Open questions

  • Which parts of Money Buddy's logic must move server-side before any public launch?
  • What gets trademarked first — 'Money Buddy', 'Buddy Suite', the buddy names?
  • Open-source any of it (as a funnel) or keep it all proprietary?
  • What's the actual pricing hypothesis for Money Buddy — and what does the free tier include?
  • Does the Buddies dashboard stay a personal tool forever, or does it become a product?

Secure Vault mechanism (the Nov 3 discussion, as confirmed)

  • Passwords are entered via Muse's secure entry card and stored in Muse's Secure Vault — not Apple Keychain / iCloud.
  • The agent can confirm a saved login exists but can never see or read the stored values.
  • Credentials reach the browser only at the moment of an approved sign-in.
  • One-time codes are never stored in the vault — held ~10 minutes as opaque references.
  • Dave can delete a saved login in the app's Settings; the agent cannot.
  • Muse's browser is server-side — the user's local device sessions/cookies do not carry into it.

BuddyOS Security & Privacy Audit

Date: 2026-10-25 · Auditor: Guardian Buddy · Requested by: Dave, via Astro (main chat) Scope: the architecture as it actually stands today — data stores and flows, access paths, credentials hygiene, third-party reality, tester-facing privacy, and a stance check against Dave's stated principles. Method: live verification against the served site and the actual repos on 2026-10-25 (gh API, unauthenticated curl probes, source inspection, connector docs). Anything not directly checked is marked unverified rather than assumed.

Verdict

Privacy-first in intention and in the private half of the architecture. Not privacy-first in fact on the public half — and the public half is the half a stranger sees.

The private architecture is genuinely well built: 187 of 192 GitHub repos are private, every buddy's working files live behind that wall, no secrets are committed in the repos scanned, the planned server fix is soundly designed, and the credential stores use read-only, single-purpose tokens where it counts. Dave's principles are real and the private side honors them.

But the public surface contradicts those principles every day it stays up. The dashboard repo is public, so all 154 buddy homepages are world-readable, including family, estate, finance, and property material — and the Neighborhood Buddy page publishes two home addresses with precise map coordinates. The registry that drives the dashboard has no privacy field at all: the rule "pages are private unless Dave says otherwise, one page at a time" exists in Dave's instructions and in our memory, but nothing in the data model represents it, and nothing enforces it. Layered under that, the browser-side GitHub token that powers the Desk is one cross-site-scripting bug away from handing a stranger read/write access to every private repo.

None of this is news Dave hasn't heard in pieces. What this audit adds is the whole picture at once, graded, with the fixes ordered. The two highest-leverage moves are both already built or already decided-in-principle: Dave's ~15-minute Firebase deploy (unlocks the token fix and the per-page gate) and Dave's pending decision on the Neighborhood page. Until those land, "privacy-first" describes where BuddyOS is going, not where it is.

Findings

CRITICAL

C1 — The public dashboard exposes personal material at fleet scale. Every buddy homepage is world-readable: names, photos, missions, status, and needs-attention items for 154 buddies spanning family (Quentin, Nancy, Emil), the estate Dave is executing (assets named, a tenant named), finances, health-adjacent work, Apple/STIX work, and property. 144 Google Doc links are listed publicly; each doc's own sharing settings still gate its contents, but the links are discoverable and requestable. The full source repo — including files not linked from any page, and the entire commit history — is equally public on github.com. Recommendation: this is the exposure the lockdown plan already addresses. Until the gate ships, consider stripping the most sensitive registry content (estate, family, finance attention items and missions) from the public build. Deleting later does not unpublish history — treat anything public today as permanently out.

C2 — Home addresses and precise coordinates are published on the Neighborhood Buddy page. Two residential addresses (Fiddletown and San Jose/Lenwood) plus latitude/longitude, verified live today. This is the single sharpest item in the audit: physical-world location data for Dave's household and his sons' home, on a page Dave has already been asked to decide on (take down vs. strip the addresses) and has not yet decided. Recommendation: decide this one first, ahead of everything else in this report. Stripping the addresses/coordinates keeps the page's civic function; taking it down entirely is cleaner. Either is a few minutes of work once Dave calls it.

C3 — A GitHub personal access token lives in browser localStorage on a public origin, and it is the keys to every private repo. Every buddy page (295 files carry the flow) reads Dave's PAT from localStorage and uses it to read and write the private buddy repos through the GitHub API — that's how the Desk, Repo files, and brain-dump features work. Any script that ever runs on the davedellaquila.github.io origin — a buggy page script, a compromised snippet, a malicious file preview — can read that key. If the token is a classic PAT, its repo scope means read and write access to all of Dave's repos; the resulting blast radius includes deleting or rewriting every buddy's files. Dave pinned this on 2026-10-21 as "real, not urgent"; the server-side fix (buddy-server, finding H2) is built and waiting only on his deploy. Recommendation: the fix is already chosen and built — deploy buddy-server and move the token server-side. In the interim, Dave should run the 2-minute manual check from the Phase 0 prep (token type, named-repo scoping, expiry) — the browser token's exact type/scope/expiry are unverified because they cannot be observed from this machine.

HIGH

H1 — The privacy principle has no representation in the system. Dave's standing rule: buddy pages are private by default, public only one page at a time, with privacy inheriting parent → child. The live registry has no privacy, visibility, or equivalent field on any of the 154 buddies. The principle is enforced nowhere; it survives only as an instruction to Astro. A new buddy is public the moment its page builds, by default, in direct contradiction of the stated default. Recommendation: add a privacy field to the registry now, default it to private, and make the build treat "private" as "shell page only — no mission, attention, or doc links baked in" until the real gate exists. That converts Dave's rule from a memo into a mechanism.

H2 — The fix for the token flow and the page gate is built but undeployed, blocked on one manual step. buddy-server (reviewed today) is the right design: Firebase Auth with an email allowlist for Dave only, ID-token verification, a strict GitHub path allowlist, the PAT in Secret Manager, and deny-all Firestore client rules. It has been waiting since 2026-10-18 on Dave's ~15-minute deploy from his own machine (Astro cannot deploy — no Firebase auth here). Every day of delay extends C1 and C3. Recommendation: schedule the deploy. It is the highest-leverage 15 minutes in the whole system.

H3 — This entire operation runs on a standard Muse VM, where Meta can review content. Per Muse's own data-handling documentation, on a standard VM interactions may be logged and reviewed by Meta for safety, security, debugging, and product improvement; conversations are not end-to-end encrypted; and conversations contribute to AI development unless the user opts out in Settings → Data Controls. Dave's buddy system — family, estate, legal-adjacent, and financial material included — flows through this channel. Dave's current opt-out status is unverified (it lives in his account settings, not observable from here). Recommendation: Dave to check the Data Controls opt-out himself. Longer term, the confidential-VM tier exists precisely for this posture; whether it fits BuddyOS is Dave's call, but the audit should name the current state plainly: Meta is a trusted party to everything, by architecture, today.

MEDIUM

M1 — No client-side encryption anywhere; GitHub, Google, and Meta can each read what they hold. Verified 2026-10-25: no git-crypt or equivalent anywhere. GitHub encrypts in transit and at rest, but GitHub can read repo contents — the protection on the 187 private repos is access control, not secrecy from the platform. The same is true of Google (Gmail, Docs, Drive, Sheets under OAuth connectors — full content), Meta's connected surfaces (Facebook, Instagram, Threads), and Plaid (bank balances and transactions via a read connector). This is not automatically wrong — it is the standard SaaS trust model — but it should be a conscious decision, not a default nobody stated. Note the sharp edge: the friend's fatal-crash case Dave is relaying runs through these channels too. Recommendation: no change required if Dave accepts platform trust knowingly. The honest sentence for the record: "private repo" means private from the public, not from GitHub.

M2 — The other public repos are mostly harmless; one carries operational detail. hello-world, preset-test, and connect-ipad-sidecar are code/test material. fiddletown-data-admin (public) is the events admin app source and includes a support-email draft naming the legacy Supabase project — low sensitivity, but it's operational detail in public, and the events stack still runs partly on that legacy Supabase project pending the Firebase migration (tracked goal). Recommendation: flip fiddletown-data-admin to private (nothing about it needs an audience) and finish the Supabase → Firebase migration so the legacy credential surface can be retired.

M3 — The tester promise is kept by policy and process, not by architecture. The onboarding guide's Privacy section promises, verbatim (guide draft, verified today): "Your pages are private by default. Nothing you say as a tester gets quoted or shared without your permission." First half: architecturally sound — each tester's buddies live in that tester's own Muse and GitHub repos; Dave's systems hold none of their buddy content by design. Second half: Dave-side systems do retain tester material — Tester Relations Buddy is explicitly Dave's memory for "what every tester has said," each tester gets a private living-dossier repo (Penny's, verified today, contains her email address and a verbatim quote of her acceptance reply), and the feedback log lives in Google Docs. Nothing there is public, and nothing suggests the promise has been broken — but "not quoted or shared" is enforced by Astro's discipline, not by the system. If a future process (a digest, a testimonial, a hire announcement) ever pulls from those dossiers casually, the promise breaks silently. Recommendation: keep the dossier/feedback retention (it's the program's memory), but treat verbatim tester quotes as consent-gated material in the process docs, and keep the guide's wording as-is only while that discipline holds.

M4 — Voice synthesis sends message text off the machine. Every spoken briefing, standup, chime, and "listen to this" sends the full message text to the platform TTS service for synthesis. The audio comes back; the text's retention on the service side is unverified. Low sensitivity per message, but the cumulative corpus (briefings, standups, crits) is a real, if modest, flow. Recommendation: awareness only — no action unless Dave wants the most sensitive material kept out of spoken form.

M5 — Page Lockdown Phase 0 is a courtesy, not a control. Verified live: robots.txt disallows everything and pages carry noindex, nofollow. Well-behaved crawlers honor it; a curious human with the URL is entirely unaffected — every page still returns 200. It should never be described, even casually, as the pages being "locked down." Recommendation: none — just keep the language honest until the real gate (H2) exists.

NOTE — what is genuinely sound

N1 — The private-repo architecture is the real thing. 187/192 repos private; buddy markdown never baked into pages; a private repo returns a plain 404 to a stranger (existence not even confirmed). Dave's specific fear from the lockdown discussion — someone editing a buddy's markdown — is covered today by repo privacy, not by the page. N2 — No committed secrets found in the dashboard repo or the server workspace (pattern scans for token/key formats), and no Supabase service-role keys in the public repos (code search). N3 — Airtable is a model citizen and on its way out. Read-only token, one base, secure credential store — and the retirement follows Dave's own data-ownership doctrine: canonical data as plain files in his own repos. The 45-attachment expiring-link episode is exactly the failure mode the doctrine exists to prevent, and it's being closed. N4 — The voting backend's Firestore rules deny all direct client access — clients reach data only through authenticated functions. That's the pattern the whole system should converge on. N5 — Tailscale is currently disconnected on Astro's VM (approval expired), so there is no live tailnet exposure to audit — and also no working private path until Dave reconnects it. N6 — Connector posture is mostly least-privilege where the platform allows it (Airtable read-only/single-base; the gh CLI token here carries repo only — no admin, no delete). The exception is inherent to classic GitHub scopes, which is precisely what the fine-grained token check (C3) addresses.
