Canonical product docs: Product brief · PRD (approved Oct 9, 2026)

1. Why, and what success looks like

Dave's direction (Oct 25): get all the bases out of Airtable into something of our own creation — probably Firebase, hopefully portable — and test the concept first with the car service history. This base is the pilot for the whole Airtable exit.

Success is not "the app reads Firestore." Success is:

If Airtable and Firebase both vanished tomorrow, Dave would still have every record and every file, in plain formats, in his own repo.

That test drives every design choice below. Firestore is a working copy the app reads. The canonical copy — the portable master — is plain data files in this repo (davedellaquila/car-buddy, private).

This plan is PRD milestone M6 (migration), feeding M7 (cutover).

3. Target design — portable master first

3.1 Canonical copy (the master) — in this repo

data/
  vehicles.json          # 28 records
  events.json            # 212 records — the PRD's service_events contract
  suppliers.json         # 15 records
  attachments/
    <event-source-id>/
      <filename>         # the real files, bit-for-bit as uploaded
  attachments-manifest.json
  source/
    airtable-export-YYYYMMDD/   # the untouched raw export the build came from

Rules:

  • Plain JSON, one record per entry, human-readable. No proprietary format, no database dump.
  • Every record keeps its Airtable record ID as source_id (e.g. rec…). Provenance survives forever; the importer (§3.2) uses it as the Firestore document ID, making imports idempotent and re-runnable.
  • Records point at files, not URLs. An event's attachments become { file: "attachments/<event-id>/<filename>", filename, content_type, size_bytes, sha256 }. No expiring Airtable URL appears anywhere in the canonical data.
  • Originals are never converted. HEIC stays HEIC, the MOV stays a MOV. Any thumbnails/previews the app wants are derived later, downstream, and are disposable.
  • The raw export is kept untouched under data/source/, so any transform decision can be audited or redone.

3.2 Working copy — Firestore (expense-tracker pattern)

  • Collections vehicles, service_events, suppliers, mirroring the canonical JSON field-for-field. Same data, two homes — by design.
  • Attachment binaries also go to Firebase Storage for the app to display, uploaded from the canonical files in the repo. Storage is a cache of the master, never the only copy.
  • If Firebase were dropped later, the exit cost is: point a new app at data/*.json + data/attachments/. That is the portability Dave asked for, and it's testable (§5, Gate 5).

3.3 Field mapping (every source field accounted for)

The importer fails loudly on any unmapped field — silent field loss is the classic migration bug, and the mapping table is the defence. Highlights:

Airtable Target Notes
Vehicles.Name / Nickname name / nickname
Vehicles.Date Sold date_sold + derived status: sold Representation is Dave's call (§6, D3)
Vehicles.Service History — dropped as a stored field Backlink; recomputed from events
Events.Vehicle (link, 0 or 1) vehicle_id (nullable) Null only for the 6 orphans (§6, D1)
Events.Work Performed by (multi-select) performed_by: [string] Verbatim. Not linked to Suppliers in v1
Events.Cost cost (number, nullable) Absent stays absent — never zero-filled
Events.Attachments attachments: [{file, …}] Per §3.1
Events.Field 9 — no target field One-off leftover; disposition is Dave's call (§6, D2)
Suppliers (all fields) same names, snake_case Directory only; nothing links in v1

New events entered after cutover write to Firestore through the app and export back to the canonical JSON in this repo (a scheduled export, part of the M7 build — the master must stay master after migration day, not just on it).

5. Phases, with verification gates

Each phase ends at a gate. A failed gate stops the line — no phase starts on a "probably fine."

Phase 0 — Approval (we are here). Dave reviews this plan and answers §6. Gate 0: Dave approves.

Phase 1 — Refresh & freeze the snapshot. Re-pull all 3 tables live; diff against the Oct 21 export (counts expected: 28 / 212 / 15; any drift gets reported, not absorbed silently). This fresh pull — not the Oct 21 file — is the migration source, because only a fresh pull carries live attachment URLs. Airtable usage pauses from here (Dave just stops adding records; the base stays readable). Gate 1: counts and diff report match expectations.

Phase 2 — Archive the 45 attachments (step zero, biggest risk). - Pilot first: download 3 files of different kinds (one JPEG, one PDF receipt, the 35.7 MB MOV) from fresh URLs; verify byte size against Airtable's recorded size metadata and open/render each one. Only when all 3 prove out does the bulk run start. - Bulk run: download all 45 in one session, immediately after a fresh pull, before URLs expire. - Build attachments-manifest.json: per file — source event, filename, content type, size (Airtable's metadata vs. actual bytes), SHA-256 checksum. Gate 2: manifest shows 45/45 files, every size matching Airtable's metadata, every checksum recorded. Any miss = re-pull and retry that file; the phase does not close with a gap.

Phase 3 — Build the canonical data. Transform scripts convert the raw export + archived files into data/*.json per §3, applying Dave's §6 decisions. Scripts live in this repo alongside the data, so the build is reproducible from data/source/ by anyone. Gate 3: automated checks pass — 28 / 212 / 15 records; 206 events with exactly one vehicle_id; orphan count matches D1's disposition; cost total across events reconciles to exactly $13,980.45; zero unmapped fields.

Phase 4 — Import to Firestore (Dave-side deploy step). Astro writes the importer (idempotent: document ID = source_id, safe to re-run) and the Firestore/Storage config; Dave runs the deploy/import from his machine on Astro's step-by-step. Gate 4: Firestore counts = canonical counts (28 / 212 / 15); Storage object count = 45.

Phase 5 — Verify in the app, Airtable still untouched. - Spot-check pack (human eyeballs, not just counts): 10 events chosen deliberately — the most recent (2026-03-19 oil change), the two 6-attachment events, an event with a PDF receipt, the Field 9 event, one orphan, one sold-vehicle event each for the Odyssey and the Twin Cam. - Read every field side-by-side: Airtable vs. app. - Portability proof: a throwaway script reads only data/*.json + data/attachments/ (no Firebase) and renders a vehicle's full history. If that works, the master really is a master. Gate 5: Dave sees the spot-check results and says the new store is trustworthy.

Phase 6 — Cutover & retire (PRD M7). App reads Firestore as its live store; Airtable base goes read-only for 30 days as the fallback (per the PRD), then Dave deletes it / lets the subscription lapse for this base. Gate 6: 30 quiet days with no need to consult Airtable.

6. Decisions — ALL DECIDED by Dave, Oct 25, 2026

Dave walked these one at a time and took the recommended option on all six: D1 (a) orphans migrate flagged Unassigned · D2 (a) Field 9 folds into Notes · D3 (a) sold vehicles kept with status: sold · D4 (a) costs migrate as-is, no backfill · D5 confirmed — performed-by stays verbatim text · D6 (a) plain files, no Git LFS. The original flagged text follows, unchanged, as the record of what was asked.

D3 AMENDED — owner correction, Oct 25, 2026 (Dave, 09:22 AM, minutes after approving): "We haven't sold the Twin Cam, we still have it." The 1959 MGA Twin Cam (recotc3D9zqQmXixb, "Twinkie") was never sold; its Airtable Date Sold (2016-08-03) is bad data and Dave's word overrules the source field. Amended D3: only the 1995 Honda Odyssey (recSTrPkeYLKyxiXF, sold 2022-06-01) gets status: sold. The Twin Cam migrates as an active vehicle — no date_sold, no sold status in the canonical data. Applied via the documented OWNER_CORRECTIONS override in scripts/build_canonical.py; the raw export stays untouched (it records what Airtable said). Corroborating detail: Airtable has the Twin Cam acquired 2016-08-11 — eight days after its supposed sale.

D1 — The 6 orphan events. Six events have no vehicle linked, so nobody can say with certainty which car they belong to. Options: (a) migrate them as-is, flagged vehicle_id: null, shown in the app under "Unassigned" until identified — recommended, nothing is lost and some may be identifiable from their descriptions; (b) Dave identifies them now from a list Astro prepares; (c) drop them. Dropping real service history is the only irreversible option on this page.

D2 — Field 9. A leftover unnamed field used by exactly one event (recAgdC029oGWzcmw). Its entire content is: "Don't know exact date they were installed. Spring 2025" — evidently a note about date uncertainty, typed into the wrong field. Options: (a) fold it into that event's Notes and drop the field — recommended; (b) preserve it as a raw custom field. Either way the raw export keeps it forever.

D3 — The 2 sold vehicles. 1995 Honda Odyssey (sold 2022-06-01) and 1959 MGA Twin Cam (sold 2016-08-03) carry Date Sold; the other 26 don't. Options: (a) keep them in the data with status: sold, included in history and lifetime totals, excluded from the active fleet and reminders — recommended; (b) archive them out of the app entirely. Note the fleet also includes vehicles Dave may no longer own but never marked sold — the plan does not guess at those.

D4 — Cost backfill. Only 28 of 212 events have a Cost. Options: (a) migrate as-is, no backfill — recommended for the migration itself; (b) a later, separate pass mining the archived PDF receipts (only 2 PDFs among the attachments, so expectations should stay low); (c) Dave backfills from memory/paper records as a side project. The migration should not be blocked on this.

D5 — "Work Performed by" stays words, not links (confirmation). The plan preserves the 16 pick-list values verbatim as text (§3.3) and does not try to reconcile them with the 15 Suppliers — they're different sets (family + local shops vs. a parts-supplier directory). A proper providers model can come in a later PRD milestone. Dave: confirm, or say if you want provider-linking pulled into this migration.

D6 — 137.9 MB of attachments in the git repo (awareness, with an option). Plain files in this repo is the portability requirement, and it works: the largest file (35.7 MB) is well under GitHub's 100 MB per-file limit. The cost is a heavier repo clone, growing with every future photo. Options: (a) plain files — recommended for this pilot, simplest and most portable; (b) Git LFS (files still Dave's, but adds a tool dependency to every clone). Dave can switch later; the manifest and layout are identical either way.

8. What this unblocks — M6, true cost of ownership

The PRD's chart contract is service_events { date, cost, vehicle_id } — exactly what data/events.json delivers. The moment Gate 3 passes, the fleet chart and MGA Buddy's ledger (which reads this same pipeline, by the Oct 12 coordination between the two buddies) have real data for the first time.

The honest launch state, in one sentence:

The chart at launch shows documented spend — $13,980.45 across the 28 events that carry a Cost — not the true total cost of anything.

13% cost coverage means the lines will read as floors, not totals, and will jump when a costly event happens to have its cost recorded. The chart ships labelled "documented spend," with the coverage (28 of 212 events) shown on its face. Any backfill (D4) improves it later without re-migrating anything — the canonical data is the chart's source, and it only gets better in place.
